## Slide Copy

### 兩層權限，兩個不同問題

**Platform Admission**

`channel／user allowlist`、Bot permission、mention mode

決定誰能把訊息送進 Runtime。

**Agent Capability**

`read-only`、`agent`、`agent-full-access`、tool／network／workspace policy

決定 Agent 進入 Runtime 後可以做什麼。

Code review → deploy 仍應分段，multi-agent 需要 trusted bot、mention 條件與 turn limit。

## Visualization Specification

- 主視覺為 Light boundary matrix，橫軸為「誰能觸發」，縱軸為「Agent 能做什麼」。
- Components：Discord／Slack Gateway、Allowlist、ACP Session、Agent Runtime、Workspace、Network／Credentials、Review Gate、Deploy Gate。
- Relations：User／Bot message → Allowlist → ACP Session；ACP Session → Runtime mode；Runtime → workspace／tools；Review result → Deploy Gate。
- Comparison：Platform allowlist 控制入口；Agent mode 控制能力；兩者都通過才能進入實際修改流程。
- Failure Path：未通過 allowlist → 不建立 session；Agent 權限不足 → 工具拒絕；權限過大但沒有外層 isolation → 進入風險區，不應直接視為可部署。

## Evidence / Limitations

- 現場筆記：Discord channel／user allowlist 決定誰能觸發；Codex mode 決定 read-only、agent 或 agent-full-access；兩層不能互相取代。
- 官方背景：OpenAB 文件描述 allowlist、bot permissions、ACP mode、trusted bot 與 max bot turns。
- 已存在 Artifact：ACP 課程 README 與 notes；沒有本地 OpenAB deployment 或 Helm release Artifact。
