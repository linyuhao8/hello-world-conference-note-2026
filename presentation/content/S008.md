## Slide Copy

### Title

Workshop 產出的部署視角

### Subtitle

預購抽選系統如何落在執行環境，並與代理商既有系統協作

### Main Message

這張圖把「我們要建的服務」與「代理商已經擁有的系統」分開，再把前者映射到雲端、辦公室與既有系統環境。讀者可以沿著責任與資料流閱讀，而不必把所有服務都視為同一個部署邊界。

### 右側重點文案

#### 本次系統

`預購抽選系統` 由四個 Container 組成：管理後台、預購 API、抽選排程與預購資料庫。這些是本次模型要描述的新增能力。

#### 執行責任

預購 API 映射到 `ECS Fargate`，抽選排程映射到 `EventBridge 排程任務`，預購資料庫映射到 `RDS for PostgreSQL`。管理後台則由代理商營運人員在辦公室電腦的瀏覽器開啟。

#### 外部依賴

代理商既有實名制 App 負責登入、實名驗證與推播通知；既有門市取貨系統接收中籤名單與取貨門市。兩者位於「代理商既有系統環境」，不屬於本次新增系統。

#### 模型中的資料流

營運人員設定活動 → 預購 API 讀寫活動規則 → 買家透過既有 App 送出已完成實名驗證的登記 → API 保存登記 → 抽選排程讀取資料並保存結果 → App 推播結果 → API 將中籤名單與門市選擇送給門市系統。

### Architecture Reading Note

這是 **Deployment View**：它回答邏輯元素被放在哪些執行環境。它不是 **Container View**，因此不在這一頁展開 API 內部的 `憑證驗證中介層`、`活動規則服務`、`登記服務` 與 `取貨服務` 的完整責任；那些責任仍由同一份 DSL 的 Container／Component model 定義。

## Visualization Specification

- **主要圖片：** 使用 Structurizr Workshop 截圖作為主要 evidence，放在畫面左側約 65% 寬度。
- **文字區：** 右側約 35% 放四個短段落，依序說明本次系統、執行責任、外部依賴、模型中的資料流。每段不超過兩至三行投影文字。
- **強調區域：**
  1. 中央的 `雲端區域`：ECS Fargate、EventBridge 排程任務、RDS for PostgreSQL。
  2. 上方的 `代理商辦公室`：營運人員電腦與管理後台。
  3. 下方的 `代理商既有系統環境`：實名制 App 服務與門市取貨系統主機。
  4. 圖中的 HTTPS／SQL 關係，作為責任與資料流的輔助標籤。
- **局部放大：** 展示層裁掉左側 Structurizr view navigator，保留右側 Deployment View 主畫布；若投影測試仍讀不清，將中央雲端區域與下方外部系統區域做兩個局部 inset。不要把局部圖當成另一個架構版本。
- **工程資料流解說：** 以右側文字描述模型定義的流向，不在圖片上新增未出現在 DSL 的箭頭。可用細線標註 `Input`、`Processing`、`Output`，但標註必須對應 DSL 關係。
- **避免的誤讀：** 不把 `RDS for PostgreSQL`、`ECS Fargate` 或 `EventBridge` 視為執行紀錄；它們是 DSL 中的 deployment mapping。

## Evidence / Limitations

### 已完成的 Workshop Artifact

- `workspace.dsl` 定義 `預購抽選系統`、兩個外部系統、Container／Component、關係與 `正式環境` Deployment View。
- Deployment mapping 明確包含：`預購 API → ECS Fargate`、`抽選排程 → EventBridge 排程任務`、`預購資料庫 → RDS for PostgreSQL`、`管理後台 → 代理商營運人員電腦`。
- `workspace.json` 保存 Deployment View 的手動版面資料，該 view 記錄 15 個 deployment elements 與 6 個 deployment relationships。
- ADR `0001-reuse-existing-realname-app.md` 狀態為 `Accepted`，決定沿用代理商既有實名制 App，不另做買家 App，也不重做實名驗證。

### 現場筆記

- 筆記把這張圖標為 Workshop 實作成果，並指出它是後續閱讀 DSL 與 ADR 的入口。
- 筆記記錄的課程主線是「先整理系統邊界、責任與關係，再用 DSL、Views、ADR 與驗證形成共同基準」。

### 官方背景

- `README.md` 說明本場是 2026-10-14 10:10–12:10 的 Lab，使用 Structurizr DSL、OpenCode V2 與 Structurizr MCP。
- 官方背景只用來說明工具與課程形式，不用來證明系統已在實際 AWS 環境運行。

### 推測或尚未驗證的部分

- DSL 使用 `正式環境` 與 AWS deployment nodes 描述目標部署模型，但 Repository 沒有實際 AWS runtime、監控、部署紀錄或 production traffic 證據。因此文案只能說「模型映射到」或「圖中描述」，不能說服務已成功部署或正在運行。
- `workspace.json` 的 workspace properties 記錄 `structurizr.inspection.error: 8`、`warning: 0`；Repository 沒有獨立的 `validate`／`inspect` 輸出可用來逐項解釋這 8 個 error。這一頁不宣稱模型已通過完整驗證，Phase 3 前應補跑並保存驗證結果。
- 圖片中的小字若在展示尺寸下無法可靠閱讀，以 DSL、workspace JSON 與本頁的短文案為準，不自行補全圖中細節。
