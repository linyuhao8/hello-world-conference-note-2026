## Slide Copy

### 四個 Gate

- **Function correctness：** API／event 是否產生預期結果？
- **Data reconciliation：** Order、Wallet、MatchEngine 的 ID、資產、狀態與數量是否一致？
- **Runtime characteristics：** latency、throughput、backlog、error 是否在相同負載下可接受？
- **Failure evidence：** timeout、deadlock、DLQ、partial failure 能否被重現、定位與處理？

### 測試條件

一筆 k6 診斷使用 `60 秒 warm-up + 900 秒 measurement`，約每秒接受 200 筆訂單，結果為 `192,000 orders → 96,000 trades`，三服務 ID／資產一致且 backlog 歸零。

### 正確解讀

這是單機、單次、特定版本的診斷結果，不是 production SLA；接受訂單也不等於完成成交。

## Visualization Specification

- 以四象限 verification matrix 為主視覺，每格固定呈現 `Input → Check → Output`：
  - Function：request／event → business assertion → expected result
  - Reconciliation：cross-service records → ID／asset／count compare → diff or match
  - Runtime：fixed workload → latency／throughput／backlog → comparable metrics
  - Failure：timeout／deadlock／DLQ → replay／diagnosis → recovery evidence
- 下方使用一條 test-condition strip：`k6 → warm-up 60s → measure 900s → ~200 orders/s → reconciliation`。
- 右側加一個小型 caution：`Queue empty ≠ background work complete`。
- 不把 192,000／96,000 畫成大 KPI；數字只作條件化 evidence。
