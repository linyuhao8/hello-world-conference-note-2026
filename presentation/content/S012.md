# S012 — 拿掉 Transaction 後，速度不能抵銷部分提交

## Slide Metadata

- **Slide ID：** S012
- **Section：** Distributed System Consistency
- **Title：** 拿掉 Transaction 後，速度不能抵銷部分提交
- **Subtitle：** 局部 settlement throughput 上升，但業務原子性與鎖順序失守
- **Main Message：** 移除事件處理器外層 Transaction 讓隔離測試更快，卻讓 SQL 可能先提交、業務檢查後失敗，並在角色交換時出現 deadlock；因此方案被拒絕。

## Slide Copy

### Candidate Change

移除事件處理器外層 `Transaction`，讓 SQL 自動提交。

### Why It Looked Faster

隔離測試的 settlement throughput：

`11,799 → 20,405 settlements/s（+72.9%）`

### Correctness Failure

SQL 提交後，Java 才檢查結算紀錄與買賣雙方 Wallet 更新；業務檢查失敗時，已提交資料不能一起回滾。

角色交換的併行情境也發現 PostgreSQL deadlock。

### Decision

**拒絕此方案。** 恢復每筆事件一個 Transaction，並依固定 Wallet UUID 順序鎖定資料列。

## Visualization Specification

- 使用三段式 decision split：`Candidate`、`Failure evidence`、`Decision`。
- `Candidate` Input：settlement event；Processing：SQL auto-commit；Output：較高局部 throughput。
- `Failure evidence` 分成兩條紅灰線：
  - `SQL committed → business check fails → partial commit`
  - `Buyer／Seller lock order differs → deadlock`
- `Decision` 箭頭回到安全方案：`per-event Transaction + fixed Wallet UUID lock order`。
- 右下角放 evidence label：`+72.9% is an isolated test result, not capacity`。
- 不重新展示 S011 的 batch SQL 數字，避免重複前一頁的採用案例。
