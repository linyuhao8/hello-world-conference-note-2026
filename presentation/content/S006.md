# S006 — 架構圖失去同步時，問題不在畫圖工具

## Slide Metadata

- **Slide ID：** S006
- **Section：** Architecture as Code
- **Title：** 架構圖失去同步時，問題不在畫圖工具
- **Subtitle：** 架構需要同時保存系統邊界、責任、關係與設計取捨
- **Main Message：** 一次性的架構圖只能呈現某個時刻的視角；若模型與決策沒有被版本控制，人與 Agent 仍可能從不同上下文理解同一個系統。

## Slide Copy

### 問題

架構圖可以說明「現在看起來怎麼連」，但不一定留下：

- 哪些系統屬於本次範圍
- 哪個元件負責哪件事
- 外部依賴由誰維護
- 為什麼選這個方案，而不是另一個方案

### 轉向 Models as Code

把架構模型放進可版本控制的 DSL，讓圖、關係與檢查可以隨模型一起更新；再用 ADR 保存決策理由與後果。

### Engineering Takeaway

架構圖的價值不在圖的數量，而在模型能否成為人與 Agent 共用、可 review、可重新產生的決策基準。

## Visualization Specification

- 使用左右對照構圖，而非列出工具清單：
  - **左：一次性圖檔**，只保留 `Rendered View`，旁邊標示 `context / ownership / why` 容易散落。
  - **右：Models as Code**，由 `System Boundary`、`Relationships`、`DSL`、`Views`、`ADR` 組成可追蹤鏈。
- 左右中間用「修改一次，是否能同步產生多個視角？」作為比較問題，不使用誇張的失敗圖示。
- 右側流程箭頭方向：`Context → Model → View → Review / Validate`；`Decision` 由 Model 連到 `ADR`。
- 每個節點顯示 Input／Output：
  - Context：需求、限制、既有系統 → model scope
  - DSL：scope、元素、關係 → versioned model
  - Views：同一模型 → 不同溝通視角
  - ADR：選項與取捨 → decision record
- 不把此頁畫成 Structurizr Deployment View；那是下一頁 S008 的 Artifact。
