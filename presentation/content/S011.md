# S011 — 交易流程的瓶頸藏在逐筆清理

## Slide Metadata

- **Slide ID：** S011
- **Section：** Distributed System Consistency
- **Title：** 交易流程的瓶頸藏在逐筆清理
- **Subtitle：** 批次 SQL 減少資料庫寫入，但採用條件仍包含跨服務對帳
- **Main Message：** 將已取得處理權的清理任務從逐筆 UPDATE 改為批次 SQL，讓寫入次數、backlog 與 p95 延遲下降，同時保留可持久化與可重試的任務邊界。

## Slide Copy

### Problem

MatchEngine 成交後需要清理暫時保留的訂單。原本約 30,000 筆清理對 PostgreSQL 執行約 30,000 次 UPDATE，寫入負擔拖慢後續處理。

### Change

保留可持久化、可重試的清理任務；只把已取得處理權的任務改成批次 SQL。

### Evidence

| 指標 | 原方案 | 批次方案 |
|---|---:|---:|
| SQL 更新次數 | 約 30,000 | 32 |
| BUY 成交速率 | 664 trades/s | 922 trades/s |
| 最大 backlog | 14,110 | 6,261 |
| Match → Wallet p95 | 13.6 秒 | 4.5 秒 |

### Adoption Gate

30,000 筆成交 ID 與資產仍核對正確，因此這個候選方案在該測試條件下採用。

## Visualization Specification

- 左側約 40% 放裁切後照片，作為 notes 中「可重跑、可追查、可接續」工程責任的現場 evidence。
- 右側約 60% 放 Before／After benchmark 與資料流：
  - Before：`30,000 cleanup tasks → 30,000 UPDATE → DB write pressure → backlog`
  - After：`claimed tasks → batch SQL × 32 → lower write pressure → downstream processing`
- 箭頭方向由 MatchEngine → cleanup task → PostgreSQL → Wallet；批次化只改變清理寫入方式，不新增服務。
- 在 benchmark 下方放小型 gate：`Throughput + latency + backlog + ID／asset reconciliation → Adopt in tested condition`。
- 不把 922 trades/s 畫成 production capacity。
