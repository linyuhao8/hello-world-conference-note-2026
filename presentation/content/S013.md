# S013 — scheduler 隔離修好吞吐，卻揭出 tradeId 推測錯誤

## Slide Metadata

- **Slide ID：** S013
- **Section：** Distributed System Consistency
- **Title：** scheduler 隔離修好吞吐，卻揭出 tradeId 推測錯誤
- **Subtitle：** 一個效能修正，讓隱藏的一致性問題在更高負載下浮現
- **Main Message：** 拆開 cleanup 與 TradeOutboxRelay scheduler 解決互相阻塞，但後續對帳發現 duplicate trade；修復流程必須保存精確 `tradeId`，不能靠 order ID 與跨程序 timestamp 推測。

## Slide Copy

### Performance Path

單一 Spring scheduler 同時處理 cleanup 與 `TradeOutboxRelay`。清理最長 9.38 秒，成交事件因此延後送到 Order 與 Wallet。

`800 orders/s：167.93 trades/s、backlog 4,090`

拆開兩個排程後：

`383.45 trades/s、backlog 246`

### Consistency Path

提高負載後，對帳發現：

`MatchEngine 42,500 trades ≠ Order／Wallet 42,499 trades`

根因：Redis reservation repair 用 `order ID + cross-process timestamp` 推測 tradeId，讓已成交買單重新回到 order book，造成 duplicate trade。

### Fix and Gate

每筆 Redis reservation 保存精確 `tradeId`，清理與修復時比對同一個 ID。修復後資料一致，但 800 orders/s 仍未通過效能關卡。

## Visualization Specification

- 使用上下兩條因果線，避免把效能改善誤畫成完整成功：
  - **上：** `cleanup + relay on one scheduler → block → split schedulers → higher throughput / lower backlog`
  - **下：** `timestamp inference → wrong repair → duplicate trade → exact tradeId → reconciliation restored`
- 箭頭方向由左至右；在中間用垂直虛線標示「更高負載揭露一致性問題」。

- 右下角放限制標籤：`Correctness fixed ≠ performance gate passed`。
- 不新增 Order、Wallet、MatchEngine 以外的服務或關係。
